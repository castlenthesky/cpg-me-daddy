# @cpg/cpg-generator

Status: flattens one parsed file's AST into a CPG subgraph for `@cpg/graph-builder` to consume.

## API (`src/index.ts`)

- `toSubgraph(parsed: ParsedFile, options?): CpgSubgraph` (`subgraph.ts`) — walks `parsed.root` pre-order, keeping only "significant" constructs (see `significant.ts`) and reparenting everything else's children onto the nearest kept ancestor, starting from `parsed.filePath` itself. Every emitted node id is `` `${parsed.filePath}::ast::${ordinal}` `` and its root edge(s) are `{ source: parsed.filePath, type: 'CONTAINS' }` — this is the tie between an AST subgraph and the file node it belongs to. `options.labelFor` overrides the default per-grammar table; `options.maxNodes` (default 500) caps output, reporting `truncated: true` rather than growing unbounded. `options.workspaceRoot` turns symbol minting on: each `METHOD`/`TYPE_DECL` with a name yields a `CpgSymbol` in the returned **`symbols` channel** plus a `DEFINES` edge from the declaration to its fqn. Symbols are deliberately *not* in `nodes` — see `@cpg/graph-builder`'s "Gotchas" for why a file must not be able to own one. Omit `workspaceRoot` and no symbols or `DEFINES` edges are emitted.
- `buildFqn` / `encodeDescriptor` / `isSymbolId` / `CpgSymbol` (`fqn.ts`) — symbol identity. An fqn is `` `<workspace-relative path>`/<descriptors> `` in SCIP's descriptor grammar (`Type#`, `name().`), and **is** the `SYMBOL` node's id. Derived from the path plus enclosing declaration names only — no ordinal, no range, no hash — which is what lets a cross-file edge survive a re-parse of the defining file. Ids are disjoint on their first character (path `/`, symbol `` ` ``, synthetic layout root a space), so `isSymbolId` is one comparison.
- `importSpecFor(node, grammar)` (`imports.ts`) — an import's module specifier, relative-dot depth, and bound names. Parses by splitting children at the child whose `type` is `import`; needs no tree-sitter field names (which `nodeToAst` drops). Python only today; TS/JS returns `undefined`.
- `ChainResolver` (`chain.ts`) — tries resolvers in order and keeps the first real answer. `resolved`/`ambiguous`/`external` stop the chain; `unresolved`/`dynamic` fall through, and the last reason survives. Order is precision-first, so a weaker link can only ever *add* answers.
- `PythonPathResolver` (`pythonPath.ts`) — resolves Python imports by probing source roots (**referencing file's own directory first**, then workspace root, `<root>/src`, then `pyproject.toml` paths), and resolves bare-name calls through this file's own definitions and its own import bindings. A member-access call gets `receiver-unknown` rather than a guess, and so does a `receiver`/`receiver-type` site — this resolver never attempts the type inference either needs. Exists because a type checker resolves nothing at all for a flat `src/` layout with no `extraPaths` — see `src/AGENTS.md`.
- `Resolver` / `RefSite` / `Resolution` / `DefinitionLookup` (`resolve.ts`) — the symbol-resolution seam. **Zero imports**, same rule as `@cpg/graph-visualizer`'s `contract.ts`, and for a structural reason: the only precise resolver calls `vscode.executeDefinitionProvider`/`executeTypeDefinitionProvider`, and `vscode` is not importable from `packages/*`, so that implementation is forced into the extension host (`src/resolve/vscodeDefinitionResolver.ts`, `REAL`) and must arrive through here. A resolver answers *where* a reference points and never *what it is called* — symbol identity stays on the graph side, so swapping resolvers can never change a symbol id and therefore can never invalidate cross-file edges other files point at. `resolve` is batch-shaped (one call per file) and must return one `Resolution` per input site, in order; an unanswerable site is `status: 'unresolved'`, never a throw and never a dropped entry. `RefKind` is `'call' | 'import' | 'receiver' | 'receiver-type'` — the last two both come from a `CALL` node's receiver token and share its `nodeId`, one asking where the receiver is bound, the other what its type is.
- `NullResolver` (`nullResolver.ts`) — `PASSTHROUGH`: answers `unresolved` for every site, so the graph is identical to one built with no resolver at all. Also the honest fallback for a language with no server installed, and the "nothing resolves" control the harness diffs against.
- `collectReferenceSites(nodes): RefSite[]` (`refSites.ts`) — turns a payload's `CALL`/`IMPORT` nodes into resolver input. Reads finished graph nodes rather than the AST, because resolution runs as a pass over the *complete* graph (a call in the first file walked can target a definition in the last). Prefers `data.refRange` for the position and falls back to `nameRange`. A `CALL` carrying `data.receiverRange` (see below) also fans out two extra sites at that position — `receiver` and `receiver-type` — sharing the `CALL` node's `nodeId`.
- `significanceTableForGrammar(grammar): Record<string, CpgLabel>` (`significant.ts`) — the per-grammar (keyed by `ParsedFile.grammar`, e.g. `tree-sitter-typescript.wasm`) node-type → `CpgLabel` table (`METHOD` / `TYPE_DECL` / `IMPORT` / `CALL` / `LOCAL`). An unrecognized grammar yields an empty table.

## Gotchas

- Emission order is pre-order (parent before children) — required by `@cpg/graph-visualizer`'s incremental `applyDelta`, which resolves a new node's seed position from its already-known parent.
- Only TypeScript/JavaScript and Python have a significance table today; other `@cpg/ast-generator` grammars yield no AST nodes (the file itself still renders).
- `GraphNode.name` is never a path — it's the construct's identifier text (or, for `CALL`, the joined callee text), falling back to the raw tree-sitter type when no name-shaped child exists.
- Every emitted node carries `data.location` (a `NodeLocation` from `@cpg/graph-visualizer`'s `contract.ts`): the file path, the construct's full `range`, and — when the construct has a name-shaped child — its identifier's `nameRange`. `nameRange` is what makes click-to-navigate land on the token: a `function_declaration`'s own `startPosition` is the `function` keyword, one token short of its name. Constructs without an identifier (import statements, anonymous arrow functions) have `range` only.
- **A `CALL`'s `nameRange` is the whole callee subtree, not the method name.** For `greeter.greet()` it starts on `greeter`, so resolving at `nameRange.start` finds the local variable rather than the method (measured: 2 of 6 calls in the demo's `src/sample.py`). `subgraph.ts` therefore also emits `data.refRange` — the **last** name-shaped leaf of the callee chain — and `collectReferenceSites` prefers it. Use `refRange`, never `nameRange`, for resolution.
- **`data.receiverRange` (a member-access call's receiver token) is deliberately conservative, not "whatever's left of the last dot".** Set only when the callee is a member-access node *and* its own first child is itself a name or another member-access chain: `greeter.greet()` → `greeter`; `a.b.c()` → `b` (the last name in the `a.b` chain, mirroring `refRange`'s own "last segment" rule); `self.x()` → `self` (resolves to a parameter, which mints no node, so no edge — by design). Omitted entirely for `f(x).g()` (receiver is a temporary) and `a[0].g()` (a subscript) — guessing the name inside either would be an actively wrong edge, worse than none. Resolving it goes through `resolvePass.ts`'s dedicated `receiver` branch, **never** `GraphBuilder.symbolAt`: `symbolAt`'s enclosing-extent fallback would snap a receiver's position to whatever `METHOD`/`TYPE_DECL` contains it (measured: `symbolAt(sample.py, 11, 8)` — the `greeter` `LOCAL`'s own `nameRange` start — returns `` `src/sample.py`/main(). ``, not the `LOCAL`).
- An `IMPORT`'s bound names come from `data.import` (an `ImportSpec`), and **one statement fans out to one `RefSite` per binding**, each positioned on the *imported* token, never the local alias (`b` in `from m import a as b` resolves to itself). Before this existed, `IMPORT` fell through `firstNameToken` — Python wraps every name in `dotted_name` — and its display name was the literal string `"import_from_statement"`.
- Positions are a parse-time snapshot, so they go stale against *unsaved* editor edits (`AstPipeline` re-parses on save). Closing that window means stamping a document version into the location and having the consumer fall back to a name search.
