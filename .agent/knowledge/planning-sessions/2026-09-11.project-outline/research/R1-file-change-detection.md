# R1 — File change detection for the cpg-me-daddy engine (macOS + Linux)

*Research date: 2026-09-11. Scope: headless Node/TypeScript daemon + VS Code host; Windows deferred.*

Legend used throughout: **[V]** = VERIFIED from docs/source fetched today (URL in Sources); **[I]** = INFERENCE / synthesis not directly stated by a source.

## Executive summary

Every serious tool in this space (VS Code, Nx, Turborepo, Watchman, rust-analyzer) has converged on the same shape: a native OS-event watcher (FSEvents on macOS, inotify on Linux) with exclusions applied *before* watches are installed, a trailing-edge debounce with a hard ceiling (50–100 ms idle / 500 ms max), explicit "rescan" handling for dropped events, and no dependence on the editor. VS Code's extension API is **not** sufficient as the source of truth: `onDidCreate/Delete/RenameFiles` fire only for user gestures inside VS Code, `onDidSaveTextDocument` only for editor saves, and `createFileSystemWatcher`'s recursive events are filtered by the user's `files.watcherExclude` (whose defaults do *not* exclude `node_modules`). For the daemon, **@parcel/watcher 2.6.0** is the recommended core: it is what VS Code itself uses, ships N-API prebuilt binaries for every macOS/Linux target we care about, prunes ignored directories (glob or path) at the native layer, batches `git checkout`/`npm install` storms into one callback (50 ms min / 500 ms max internal debounce), and offers `writeSnapshot`/`getEventsSince` for catch-up after daemon restarts. Its two gaps — no rename events (renames = delete + create) and no exposed "events were dropped" signal — are closed by an inode/hash pairing heuristic and a periodic hash-walk reconciliation. The VS Code host should contribute only *hints* (save → fast-path that file; explorer rename → exact old/new pair) and never be the only watcher.

## 1. VS Code APIs

**What fires for edits made outside VS Code (terminal agent, `git checkout`)?**

- `workspace.onDidSaveTextDocument` — "emitted when a TextDocument is saved to disk" [V]. It is an editor event; **[I]** it does not fire for external writes (there is no TextDocument save involved).
- `onDidCreateFiles` / `onDidDeleteFiles` / `onDidRenameFiles` / `onWillRenameFiles` — **[V] verbatim**: "This event is triggered by user gestures, like renaming a file from the explorer, and from the `workspace.applyEdit`-api, but this event is *not* fired when files change on disk, e.g triggered by another application, or when using the `workspace.fs`-api." Also: "When renaming a folder with children only one event is fired." So these are useless for terminal-agent edits and `git checkout`, but they are the **only** API that gives a true old→new rename pair for in-editor renames. Known gaps even inside VS Code: explorer copy/paste and drag/drop (#143557), SCM "Discard All Changes" (#156925) [V].
- `workspace.createFileSystemWatcher` — does reflect on-disk changes from any process (it is backed by the OS watcher) [V]. Doc facts [V]: all workspace folders are watched recursively by default; a `RelativePattern` whose `base` is outside the workspace is watched **recursively if the pattern is "complex" (`**` or path segments), otherwise non-recursively**; a plain `string` pattern "cannot be used to add more folders … nor will it report any file events from folders that are not part of the opened workspace"; a deleted watched path suspends the watcher until re-created; "file events from deleting a folder may not include events for the contained files … performance optimizations are in place to fold multiple events that all belong to the same parent operation … into one event"; "file events from recursive file watchers may be excluded based on user configuration (`files.watcherExclude`) … it is highly recommended to watch with simple patterns that do not require recursive watchers where the exclude settings are ignored". Correlated watchers with custom excludes exist only as a proposed API, and "event correlation is disabled again for TS extension given instability in parcel watcher" (Sept 2024) [V].

**Renames vs delete+create.** `FileSystemWatcher` has only `onDidCreate/onDidChange/onDidDelete` [V]. VS Code's parcel adapter maps `create→ADDED`, `update→UPDATED`, `delete→DELETED` with **no rename correlation** [V]. Its `coalesceEvents` then flattens DELETE→CREATE of the same path into UPDATED, drops CREATE→DELETE, keeps CREATE over a following UPDATE, and drops child DELETEs under a deleted parent [V] — good for atomic saves (see §5), bad for rename detection.

**Latency / debounce chain [V]:** parcel native debounce (50 ms idle, 500 ms max) → `FILE_CHANGES_HANDLER_DELAY = 75` ms ("Parcel internally uses 50ms as delay, so we use 75ms") → `ThrottledWorker { maxWorkChunkSize: 500, throttleDelay: 200, maxBufferedWork: 30000 }` → extension host. **[I]** Expect ~130–800 ms from disk write to extension callback in a single-file case, longer under load; it does coalesce bulk operations because parcel does.

**Under the hood [V]:** recursive = `@parcel/watcher` with backend `isWindows ? 'windows' : isLinux ? 'inotify' : 'fs-events'`; non-recursive = Node `fs.watch`. Watcher restarts after errors with 800 ms delay; missing paths are polled with `fs.watchFile` every 5007 ms.

## 2. Node-side libraries for the headless daemon

See table for the per-library facts; additional notes:

- **@parcel/watcher** exposes `subscribe(dir, cb, {ignore, backend})`, `writeSnapshot`, `getEventsSince` (returns the same event shapes) [V]. Backend priority is FSEvents → Watchman → inotify → Windows → kqueue, and the README notes FSEvents/Watchman are "significantly more performant than the brute force backends" for *querying* [V]. Because Watchman is a selectable backend, a user who has Watchman installed gets Watchman's settle/VCS logic for free with no code change [I]. Requires `node >= 10` [V].
- **chokidar 5** is pure JS and ESM-only [V]; its `atomic` filter is exactly the temp-file+rename heuristic we would otherwise write [V]; `awaitWriteFinish` polls size until stable (2 s default — far too slow for a 2 s SLA unless lowered) [V].
- **Node `fs.watch`**: on Linux the recursive implementation is JavaScript (`lib/internal/fs/recursive_watch.js`) that installs "one fs.watch() per directory" and re-reads directories on events [V]; it now has an `ignore` option [V] (version-added not in the history table I fetched [I]). No batching, `rename` is ambiguous (create, delete, or rename all report `'rename'`) [V].
- **inotify limits [V]:** `/proc/sys/fs/inotify/max_user_watches`, `max_user_instances`, `max_queued_events`; excess queued events are dropped but `IN_Q_OVERFLOW` is always generated; since kernel 5.11 the default `max_user_watches` is 1 % of RAM clamped to [8192, 1048576] (commit 9289012). Node surfaces exhaustion as `ENOSPC` on `fs.watch` **[I]**, and VS Code shows a notification pointing at `fs.inotify.max_user_watches` [V]. Detection recipe **[I]**: at startup on Linux read `/proc/sys/fs/inotify/max_user_watches`, compare with the directory count from the initial walk (after excludes), and warn/print the `sysctl` fix if within 20 %.
- **FSEvents pitfalls [V]:** events are coalesced by a `latency` window; a directory event and subdirectory events "may be coalesced into a single event" flagged `kFSEventStreamEventFlagMustScanSubDirs`, and on `KernelDropped`/`UserDropped` "you must do a full scan of any directories that you are monitoring". Event IDs persist across reboots (`sinceWhen`). Neither @parcel/watcher nor chokidar exposes these flags to JS **[I]** — so a periodic reconciliation walk is mandatory on macOS.

## 3. Bulk-change detection (prior art)

- **@parcel/watcher**: native debounce; "a single notification will be emitted with all of the events at the end" of `git checkout`/`npm install` [V]. Ceiling 500 ms means a long checkout arrives as several 500 ms chunks [I].
- **Watchman**: `settle` 20 ms [V]; since 3.2, "if the root appears to be a version control directory, subscription notifications will be held until an outstanding version control operation is complete (based on the presence of either .hg/wlock or .git/index.lock)" (`defer_vcs`) [V]; `state-enter`/`state-leave` let tools defer or *drop* everything inside a named state such as `hg.update` [V]; SCM-aware `since: {scm: {"mergebase-with": "main"}}` queries return only the local commit-stack delta "despite there being hundreds of files that were physically updated" [V].
- **Nx** (native Rust watcher on `notify = "=9.0.0-rc.5"`) [V]: `IDLE_WINDOW = 100 ms` trailing debounce, `MAX_WAIT = 500 ms` "starvation cap", `RESCAN_MAX_WAIT = 2 s` — on notify's `Rescan` flag (e.g. inotify overflow) "the next flush emits a single rescan event instead" of per-path events; ignores come from `.nxignore` > `.gitignore` > git excludes via the `ignore` crate [V]. Docs: changes arriving during a command are batched and run after it completes [V].
- **Turborepo** (`notify` + `fsevent-sys`) [V]: 10 ms debouncer; any event touching git control files is converted into an invalidation "Git index or exclude state changed"; `need_rescan()` → invalidation "file watching backend requires a full rescan" [V]. I.e. Turbo treats a `.git/index` change as "throw away incremental state and re-derive" [I].
- **rust-analyzer**: `files.watcher` default `"client"` (LSP `didChangeWatchedFiles`), `"server"` uses `notify 8.2.0` with `RecursiveMode::Recursive` [V].
- **tsserver**: `watchOptions` (`useFsEvents` default on macOS/Windows; Linux has no native recursive watching so one watcher per directory; `synchronousWatchDirectory:false` = coalesce; `excludeDirectories`) [V].
- **git fsmonitor--daemon**: watches the worktree with inotify/FSEvents and synchronises via cookie files it creates inside `.git` then waits to observe [V] — a neat "is the event stream caught up?" trick we can copy [I].

**Is `.git/HEAD` / `.git/index` a reliable signal?** `.git/index.lock` presence is used by Watchman as the canonical "VCS operation in progress" gate [V], and git writes the index by creating `index.lock`, writing, then renaming [V]. **[I]** `HEAD` only changes on branch switches (not `git checkout -- <paths>`, `stash`, `merge`), while `index.lock` appears for nearly every mutating git command, including trivial `git add`. Conclusion: use `index.lock` as a *hold* signal (defer cascade while present, bounded), use `HEAD`/`ORIG_HEAD`/`refs/**` changes as a *hint that a bulk event is likely*, and rely on burst counting as the actual trigger. Prior art for "N events in T ms → batch mode": parcel's 500 ms max-wait and Nx's `MAX_WAIT` are time ceilings, not counts; a count threshold is our own addition [I].

## 4. Rename / move detection

- **True rename events:** Linux inotify emits `IN_MOVED_FROM`/`IN_MOVED_TO` pairs "matched up via their shared cookie value", but they are "not guaranteed to be consecutive" [V]. macOS FSEvents (with `kFSEventStreamCreateFlagFileEvents`) sets `ItemRenamed` on events for the involved paths [V]; **[I]** distinguishing old from new requires a `stat` (old path gone, new path present). Rust `notify` surfaces `RenameMode::Both` from cookies and `notify-debouncer-full` pairs From/To "via file IDs" [V]. Among Node libs only **nsfw** exposes `RENAMED {oldFile,newFile}` [V]; @parcel/watcher, chokidar, Node `fs.watch` and VS Code all degrade to delete+create [V].
- **Standard heuristic when you only get delete+create [I]:** within one batch (or a ≤500 ms window) pair each `delete(A)` with a `create(B)` where (a) `fs.stat(B).ino/dev` equals the inode we recorded for A (rename(2) preserves the inode on the same filesystem), or (b) content hash of B equals the stored hash of A and sizes match. The CPG already needs per-file hashes for no-op detection, so (b) is free; (a) requires persisting `ino`+`dev` per file node. Treat a match as `rename` (rewrite path property, keep node identity, re-resolve imports), otherwise delete + reparse.

## 5. Save semantics of editors

- **VS Code text saves are *not* atomic**: the maintainer describes the current behaviour as "truncate the file to 0 bytes" then "write the contents" and the atomic-save request (#98063, opened 2020) is still open/Backlog with no setting [V]. Downside he cites for atomic mode: "some external file watchers might be confused about a file constantly being replaced" [V]. VS Code *does* write user data (`settings.json`, `keybindings.json`) atomically with a new inode (#195539) [V] — irrelevant to workspace sources. **Watcher view:** a single `update` (parcel) / `change` (chokidar); **[I]** a reader that reacts within microseconds can observe a 0-byte file between truncate and write.
- **Vim**: `'backupcopy'` — "yes" copy & overwrite, "no" "rename the file and write a new one", "auto" pick what works; Vi default "yes" on Unix, otherwise "auto" [V]. Help text warns that "no"/"auto" break "several file-watcher daemons like inotify" because the watched inode becomes the backup [V]. **[I]** With rename-mode saves the watcher sees delete(A)+create(A) (parcel) or rename+rename (`fs.watch`); VS Code's coalescer turns that into UPDATED; chokidar's `atomic` (100 ms) does the same.
- **JetBrains "safe write"**: "a changed file is first saved in a temporary file. If the save operation succeeds, the file being saved is replaced with the saved file. (Technically, the original file is deleted and the temporary file is renamed.)" [V]; webpack's troubleshooting doc tells users to turn it off [V]. **[I]** default is on (widely reported; the help page I fetched does not state it).
- **Zero-byte race:** real for truncate-then-write editors (VS Code) and for any tool doing `fs.writeFileSync` in two syscalls [I]. Mitigation used by chokidar (`awaitWriteFinish`) is size-stability polling [V]. For a 2 s SLA the cheaper answer is: debounce ≥ 50 ms after the last event for that path, then read + hash; if size is 0 and the previous version was non-empty, re-check once after 100 ms before applying [I].

## Recommendation for cpg-me-daddy

**Library choice.** `@parcel/watcher` 2.6.0 in the daemon (prebuilt N-API, MIT, same engine as VS Code, native ignore pruning, batch semantics, snapshot catch-up). Fallback chain if the native binary fails to load: `@parcel/watcher-wasm` → `chokidar` 5 (with `atomic:true`, `ignored` function). Skip nsfw (compile-on-install) and raw `fs.watch` (no batching, ambiguous events). If `watchman` is on `$PATH`, allow `backend: 'watchman'` as an opt-in.

**Excludes.** Compute once at startup: hard-coded (`**/node_modules/**`, `**/.git/**` except the control files below, `**/dist/**`, `**/out/**`, `**/__pycache__/**`, `**/.venv/**`, `**/.turbo/**`, `**/.nx/**`) ∪ parsed `.gitignore` chain (root + nested, `ignore`-crate semantics) → pass as parcel `ignore` globs so no watch/descent happens; re-apply the same matcher post-hoc on every event (belt and braces, and needed for the fallbacks). Watch `.git/HEAD`, `.git/index`, `.git/index.lock`, `.git/refs/**` non-recursively via a second, tiny subscription.

**Debounce / coalesce / bulk policy (numbers to start the spike):**

| Stage | Rule |
|---|---|
| Native | parcel batches (50 ms idle / 500 ms max). |
| Per-path settle | Trailing debounce **100 ms**, ceiling **500 ms** (Nx numbers). Coalesce per path: delete→create ⇒ change; create→delete ⇒ drop. |
| No-op filter | Hash file; if equal to stored hash → drop (covers `git checkout` touching identical files, formatters, `touch`). |
| Zero-byte guard | If new size is 0 and old was not → re-read after 100 ms before applying. |
| Rename pairing | Within a batch, pair delete(A)/create(B) by stored `ino`+`dev` (via `fs.stat`) else by hash → `rename`. |
| Bulk mode entry | Any of: batch ≥ **200** paths, or ≥ **50** distinct directories, or `.git/index.lock` exists, or `.git/HEAD` changed in the last 2 s, or ≥ 500 raw events in 1 s. |
| Bulk mode behaviour | Hold the dependent cascade; keep hashing/parsing changed files; exit when quiet for **750 ms** *and* `index.lock` is gone, hard cap **10 s**. Then compute the changed set, topologically order the cascade, run one graph transaction. |
| Dropped-event safety | On watcher error/restart, or every 10 min idle, run a reconciliation walk (mtime+size, hash on mismatch) against the stored file nodes; on daemon start use `getEventsSince(snapshot)` and fall back to the walk if the snapshot is missing/older than 24 h. |
| Linux limits | Read `/proc/sys/fs/inotify/max_user_watches`; warn with the `sysctl` fix if the directory count is within 20 %; on `ENOSPC` degrade to polling for the affected subtree. |

**VS Code host complement.** The extension does not run its own recursive watcher when the daemon is present. It forwards `onDidSaveTextDocument` as a *priority hint* (daemon skips the 100 ms debounce for that path but still hashes), and forwards `onWillRenameFiles`/`onDidRenameFiles` as authoritative rename pairs for in-editor renames. If the daemon is unavailable, the extension falls back to `createFileSystemWatcher(new RelativePattern(folder, '**/*'))` knowing events are subject to `files.watcherExclude` and that no rename information exists.

**Spike experiments (each ≤ half a day):**
1. Parcel latency histogram on macOS and Linux: single-file save from VS Code, vim (`backupcopy=auto`), JetBrains safe-write, and `echo > file` from a terminal — confirm event shapes and time-to-callback; verify the delete+create pairing for vim/JetBrains.
2. `git checkout` between two branches differing in 2 000 files in a repo with 50 k files under `node_modules`: count batches, sizes, wall-clock from first to last event; confirm `node_modules` produces zero events with parcel `ignore` and that `.git/index.lock` appears before the first worktree write and disappears after the last (this is the key **[I]** to validate).
3. `npm install` / `pnpm install` and a codegen run writing 5 000 files inside an *unignored* directory: check whether the count/directory thresholds trip bulk mode and whether any events are lost (compare against a post-run hash walk).
4. FSEvents drop test: generate >10 k events/s on macOS and confirm the reconciliation walk catches what parcel missed (parcel exposes no drop flag).
5. Linux inotify exhaustion: set `max_user_watches=8192`, open a repo with 20 k directories, observe the error path and the fallback.
6. Rename pairing accuracy: `git mv` 500 files, IDE-driven folder rename, `mv` across filesystems (inode changes → hash fallback), and rename-then-edit within 500 ms.
7. Daemon restart: kill -9 mid-storm, restart, verify `getEventsSince` + walk converge on the correct graph within the 2 s budget for small deltas.
